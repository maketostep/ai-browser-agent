# Фаза 0 — исследование

Цель фазы: снять неопределённость по трём вопросам, от которых зависит вся архитектура,
и подтвердить ответы измерениями, а не документацией.

## Вопрос 1. Как отдавать состояние страницы модели?

ТЗ запрещает слать страницу целиком. Нужно было понять, насколько всё плохо и что даёт
готовый инструментарий. Замеры на `lavka.yandex.ru` (реальная цель, не тестовый стенд):

| Представление | Размер | К raw HTML |
|---|---|---|
| Raw HTML | 430 954 симв. | 1× |
| Playwright `locator.ariaSnapshot()` | 7 153 симв. | 60× |
| **Собственная дистилляция DOM** | **2 321 симв.** (63 интерактивных элемента) | **186×** |
| `document.body.innerText` | 1 976 симв. | — |

Вывод: raw HTML — это ~120k+ токенов на одну страницу, то есть неприемлемо даже при 1M
контекста (дорого, медленно, шумно). Собственная дистилляция даёт ещё 3× сверх
Playwright-снапшота, потому что выкидывает всё неинтерактивное и не дублирует вложенность.

## Вопрос 2. Как агент адресует элемент, если селекторы нельзя хардкодить?

Рассмотрено три варианта:

1. **`page._snapshotForAI()` + `aria-ref`** — то, что внутри использует Playwright MCP: снапшот
   с готовыми рефами `[ref=e11]`. **Отклонён:** в Playwright 1.63 этого метода на `Page` нет.
   Рантайм-проверка членов прототипа `Page` вернула только `ariaSnapshot`, `ariaSnapshotJSON`.
   Публичный `ariaSnapshot()` рефов не содержит — по нему кликать нечем.
2. **Sub-agent возвращает CSS-селектор по куску HTML** — подход кандидата с оффером (видно на
   скринах: `#search-input-id`, `.buttonRight__sJjK3`). Работает, но упирается в обфусцированные
   классы и требует лишнего round-trip к модели на каждый клик.
3. **Собственные рефы, проставляемые в рантайме** — выбран. Проход по DOM помечает каждый
   видимый интерактивный элемент атрибутом `data-agent-ref="eN"`, модель видит строку
   `[e3] searchbox "Поиск"` и возвращает `e3`, харнесс кликает по `[data-agent-ref="e3"]`.

Вариант 3 проверен end-to-end: агент выбрал `[e3] searchbox "Поиск"` только из дистиллированного
текста, харнесс кликнул и ввёл текст по рефу, страница ушла на
`/search?text=%D1%85%D0%BE%D1%82-%D0%B4%D0%BE%D0%B3`. Ни одного селектора не зашито — реф выдан
в рантайме. После перехода снапшот пересобирается (85 элементов), рефы живут только внутри
одного наблюдения.

## Вопрос 3. Что ломается на реальной странице?

- **Модальные окна съедают a11y-дерево.** Первый замер `ariaSnapshot()` вернул 290 символов —
  не потому что страница пустая, а потому что открытый `[role=dialog]` с `aria-modal` обрезает
  дерево до себя. Агент, работающий только на a11y-снапшоте, в этот момент «слепнет» и не видит
  ничего, кроме попапа. Собственная дистилляция от этого не страдает, но поведение надо знать:
  **первым шагом на любой новой странице агент должен уметь распознать и закрыть попап.**
- **Chrome вместо bundled Chromium.** Система Chrome найден, используем `channel: "chrome"` —
  меньше поводов для антибота, чем у Playwright-сборки.
- **Персистентная сессия.** `launchPersistentContext(profileDir)` — профиль на диске, ручной
  логин пользователя переживает рестарты процесса. Это требование ТЗ закрывается штатно.

## Принятые решения

| Решение | Выбор | Причина |
|---|---|---|
| Браузер | Playwright + `launchPersistentContext`, `channel: "chrome"`, `headless: false` | ТЗ требует видимый браузер и persistent session |
| Наблюдение | Своя дистилляция DOM + рефы `data-agent-ref` | 186× сжатие, адресация без хардкода селекторов |
| Модель | `claude-opus-5`, adaptive thinking, `effort: high` | Многошаговое агентное рассуждение |
| Цикл | Ручной streaming-луп (`messages.stream` + `finalMessage`) | Нужен контроль над историей, гейтом и печатью вызовов в терминал |
| Sub-agent | `claude-haiku-4-5` для точечных вопросов по DOM | Тяжёлое чтение не попадает в основной контекст |
| Контекст | Дистилляция + прунинг старых наблюдений + `clear_tool_uses` | Три уровня вместо одного |

## Дополнено на фазе реализации

**`__name is not defined`.** При переносе дистилляции с POC (`.mjs`) на TypeScript она
начала падать в странице на каждом вызове. Причина: `tsx` компилирует через esbuild с
`keepNames`, тот оборачивает внутренние функции в хелпер `__name`, а Playwright переносит
функцию в страницу через `toString()` — хелпера в странице нет. Лечится шимом, который
отправляется в страницу строкой и потому не проходит через компиляцию. Баг не мог
проявиться на POC: чистый `.mjs` не компилируется.

**Два разных числа сжатия.** 186x из таблицы выше — это только список интерактивных
элементов, сопоставимо с `ariaSnapshot`. Наблюдение, которое реально уходит в модель,
включает ещё видимый текст страницы и метаданные: 4 648 символов против 433 953, то есть
93x. В README приведены обе цифры с пояснением, какая за что отвечает.

**Молчаливый `catch` вокруг обхода фреймов.** Исходно ошибка любого фрейма глушилась как
«фрейм мог отсоединиться». На деле это означало, что провал ГЛАВНОГО фрейма выглядит для
агента как пустая страница, и он уверенно идёт принимать решения вслепую. Теперь провал
главного фрейма попадает в наблюдение явным предупреждением.

**Headless ловит антибот.** При проверке профиля в headless Лавка отдала `403` и 2 972
символа вместо 452 561. Тот же профиль и тот же код в headed-режиме проходят штатно.
Продукт по требованию ТЗ и так работает headed, но вспомогательные скрипты нельзя
гонять в headless: диагностика будет врать. В `scripts/smoke-observe.ts` headless теперь
включается только явным `SMOKE_HEADLESS=1`.

**Снимок SPA нестабилен во времени.** Фиксированная пауза 700 мс после действия давала
на одной и той же странице Лавки от 15 до 64 интерактивных элементов - как повезёт с
моментом. Агент, которому досталось чтение на 15, видит почти пустую страницу и решает
вслепую, причём молча: ошибки нет, просто неполные данные. Заменено на ожидание
стабилизации (число интерактивных элементов не меняется между двумя проверками,
шаг 250 мс, потолок 3 с). После правки четыре прогона подряд дают ровно 64 элемента.

**Персистентный профиль загрязняет измерения.** Корзина, история и персонализация
переживают перезапуск - это требование ТЗ, но оно же ломает сравнение прогонов: второй
прогон демо-сценария прошёл за 3 шага вместо 15 не благодаря правке, а потому что товар
уже лежал в корзине с прошлого раза. Перед записью видео и перед любым замером корзину
надо чистить руками.
